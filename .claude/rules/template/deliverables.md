## 進捗報告のルール

- **途中経過は Issue のコメントに Markdown で報告**
  - コードを書いた後、コミット前に進捗を Issue に報告
  - 報告内容：
    - 完了した作業
    - 現在のブロッカー（あれば）
    - 次のステップ

### ★ セッションの区切りと引き継ぎ

1 本のセッションで独立した仕事を続けると、呼び出しのたびに膨らんだ文脈全体を読み直すため費用が増え続ける。
**独立した仕事ごとにセッションを区切る。** エージェントは /clear・/compact を実行できないので、区切りでは次を行う。

- **区切り**: PR をマージした後／関係のない issue に移るとき／長い中断（日をまたぐ等）の前。
- **引き継ぎを issue に書く**: `bash scripts/handoff.sh write <issue番号> <本文ファイル|->`。見出しは
  `### 済んだこと` `### 決まったこと` `### 次の一手` `### 未解決の問い` の 4 つ（該当なしは「なし」。
  欠けるとスクリプトが投稿を拒む）。
  次のセッションがこれだけで再開できるように書く。書き先は続きの作業がある issue（マージ後なら親 task）。
  ユーザーが確定した前提は引き継ぎではなく `premises.md` の置き場所に書く。
- **ユーザーに 1 行で伝える**: 「区切りです。/clear をどうぞ（同じ流れの続きなら /compact）。」
- 次のセッションでは SessionStart フック（`scripts/session-context.sh`）が最新の引き継ぎと epic 前提を読み込む。
  別の issue を続けるときは `bash scripts/session-context.sh <issue番号>`。
- /compact の要約はサブエージェントにも別のセッションにも見えない。残すべきことは要約に頼らず引き継ぎに書く。


### 運用受入の観測ログ

通常のタスクで共有開発基盤の動作を観測したときは、引継ぎ・完了コメントに次を追記する。
未実行項目のために通常タスクを止めたり、受入専用の作業を毎回追加したりしない。
実際に発生した品質 FAIL・必読欠落・委任失敗は既存の停止条件に従う。

```markdown
### 共存基盤の確認
- Agent / CLI バージョン: Codex / 取得できた版（不明なら不明）
- 項目: 独立レビュー
- 結果: PASS / FAIL
- 観測: 別 reviewer の起動と結果受領を確認
- 未確認範囲: セッション再開
```

- タスクのコメントを証拠の正本とし、初回成功・失敗・挙動の変化だけ集約する。同じ条件の成功は繰り返し転記しない。
- リポジトリの open な `validation` Issue から、本文に `## 運用受入ログ` があり、対象が一致する追跡先を確認する。
  番号は共通ルールに固定しない。該当先がない場合は通常タスクの記録のみ、複数なら対象の明確なものを選び、曖昧ならリンク先未確定と記録する。
- 追跡 Issue の既存表・コメントを確認し、新しい観測だけ、項目・Agent・結果・証拠コメント URL を追加する。
  記録漏れや投稿失敗は明記し、未集約リンクを引継ぎに残す。確認できないことを PASS にしない。
- 指示・設定・フック登録の存在は動作実証ではない。hook の自動注入と手動読込、CLI 版・実行条件を区別する。
  未使用スキル・未観測の分岐は未確認のまま残し、代表例から全スキルの成功を推定しない。
- 失敗は既存の不具合 Issue を確認し、必要なら `issue-create` で切り出してリンクする。生ログは必要時だけ保存する。
  別リポジトリ・公開上流への転記は自動で行わず、プロジェクト固有情報や認証情報を公開しない。
