## Issue 階層

Issue は **epic / task / issue の3層**。親子は **GitHub ネイティブの sub-issue**、種別は**ラベル**で表す。

| 層 | ラベル | 役割 | worktree | マージ |
|---|---|---|---|---|
| **epic** | `epic` | ゴール。task をまとめる | 持たない | しない |
| **task** | `task` | 1つのまとまった仕事 | 持たない | しない |
| **issue** | 種類ラベル | 実作業 | **1つ持つ** | **個別にマージ** |
| 小タスク | — | 分割不要な粒度 | 親と共有 | 親と一緒 |

worktree を持つのは issue 層だけ。task 内の各 issue を個別にマージし、main との乖離を溜めない。

### 既定の task 構成（必須）

task の下に次の順で issue を置く。**省略する場合は task 本文に理由を書く。**

```
task
 ├─ 1. survey       既存手法・先行研究の調査（novelty / baseline 監査）
 ├─ 2. spec         仕様の作成・レビュー
 ├─ 3. feature      実装
 ├─ 4. validation   実装は仕様どおり動くか（実装の正しさ）
 └─ 5. experiment   仮説は正しいか（設計の正しさ）
```

| task の種類 | 既定の構成 |
|---|---|
| 新手法の検証 | survey → spec → feature → validation → experiment |
| 既存実装の改善 | spec → feature → validation |
| バグ修正 | bug（単独） |
| 調査のみ | survey（単独） |
| 基盤整備 | spec → feature → validation |

- **`validation` が PASS して初めて `experiment` の negative を信じてよい**（設計の誤りと実装バグを切り分けるため）。
- **survey を先頭に置く**のは「既存手法で既に解けるか」の監査を手順にするため（後回しにして、複数段の後に古典手法で
  解けると判明し全結果が無価値になった失敗がある）。**2周目以降も skip しない。** 内容は「ここまでの結果を踏まえて
  追加サーベイが必要か」の検討で、不要でも判断の記録を残して閉じる（結果が出るたびに探すべき場所が変わる）。

### ★ ゴールの不変性

- **epic の goal は変更しない。** 追加 task を作るときは goal を読み直し「この goal に照らして必要か」で判断する。
- **結果に合わせて goal を書き換えるのは禁止**（以降の判断が新しい goal 基準になり、ずれが自己強化する）。
  変える必要があれば**新しい epic を立て**、旧 epic は「この goal は達成されなかった」記録として閉じる。

### ★ goal を小さく読まない（書き換えの逆方向）

goal を守ろうとして範囲を勝手に狭めるのも同じ害がある（先行 A の FAIL を理由に、完了条件に明記された B・C の測定を
未着手のまま epic ごと閉じた失敗がある。否定的な判定を出すこと自体が達成条件だった）。

- **閉じる前に完了条件を1項目ずつ照合する。** 未充足が1つでもあれば閉じない
- **未着手の子を落とす根拠は、完了条件に明示されているかで判断する。** 明示が無ければユーザー判断を仰ぐ
- **先行の失敗を理由に後続を落とすなら、同じ仮説を検証しているかを確認する。** 別の仮説なら左右しない

判定の実体は `auto-reviewer`（停止条件 S7 / S8）と `/review-spec` の「epic goal 整合チェッカー」。

### ★ goal は「正しい情報の獲得」にする（数値比較を goal にしない）

**「指標 X が baseline / 閾値を超えること」を goal・完了条件にしない（全面禁止）。** goal は
**「正しい情報を得ること／正しく測って判定を出すこと」** にする。数値超えを goal にすると、低いときは判定を出せずに止まり、
高いときは silent-wrong・交絡でも達成と誤認し、高くするために不当な手段（baseline 弱体化・循環・チェリーピック・
指標の後付け変更）を使い始める。

- **goal・完了条件は「測定/判定」の言葉で書く。**
  ✗「recall@40 が 0.686 を超える」 → ○「recall@τ を**非循環・母数明示で正しく測り**、律速を切り分けて**判定を出す**」
- 数値は判定の材料。比較は experiment の中で行うが、超えること自体を達成条件にしない。**negative も、正しく測れていれば達成。**
- 予想と違う結果は原因を特定するまで結論にしない（`experiment-discipline.md` 規律5）。
- **epic / task / experiment のすべての goal に適用する。** `/task-start`・`/review-spec`・`auto-reviewer` が確認する。

### 新規タスクの流れ

`/task-start`（task 作成・子 issue 生成・実行確認）→ `/task-run`（または `/issue-start` で個別に着手。ブランチと worktree を作る）
→ `/issue-finish`（issue ごとにマージ。溜めて一括マージしない）。
**Issue の作成は `/issue-create` が単一情報源。** 他のスキル・手作業で `gh issue create` を直接呼ばない。

### ★ 現在の状態と目標の状態を必ず対話で確認する

**ユーザーはほとんどの場合、十分な説明をしない**（本人に自明な前提は言語化されない）。目標だけでなく**現状の認識もずれている**。
task は「現在地から目的地までの距離」なので、両方を合意する。

- **受け取った説明をそのまま記録しない。** 両側を能動的に聞き出す
- **平易な言葉で聞く。** 「成功条件を定義してください」ではなく本人の言葉で答えられる質問にする
- **答えられない項目は推測で埋めない。** 「未確定」として残し、**解消担当（`→ survey` / `→ spec` / `→ #番号`）を必ず併記する**。
  担当のない未確定は「誰も確定させないまま実装に入る」ことを意味し、`/task-run` はこれを停止扱いにする
  （記述形式の定義は `/task-start` Step 4、判定表は `/task-run` Step 0-2）
- **短い依頼を自分の解釈で目的化しない。** 直前の議論のどの課題に属するかを1文で言い直して確認する
- **疑問形・感想は指示ではない。** 答え（比較・利点・欠点）を返すにとどめ、採用・記録は明示の指示を待つ
- **現状は task ごとに確認し直す。** 前の task の記述を引き継がない

確認の頻度を下げる運用（自走を許す運用）でも、この節の確認は省かない。質問の型は `/task-start`。

### Git Worktree の使用（必須）

並行タスクのブランチ混入を防ぐため、issue ごとに **`worktrees/`（ドット無し、`.gitignore` 対象）** に
`scripts/worktree-relative.sh add` で worktree を作る（`.git` 参照を相対パスにする。`git-workflow.md`）。
