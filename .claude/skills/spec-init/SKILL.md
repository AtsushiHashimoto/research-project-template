# Spec Init

`auto-reviewer` が必読とする `.spec/` の3ファイルに、**プロジェクト固有**の内容を対話的に追加します。

```
/spec-init
```

`/worktree-init` からも呼ばれます。単体で何度でも再実行できます。

## 前提: 既定は同梱済み

3ファイルには**実プロジェクトの失敗実績から抽出した既定**が既に入っています。

| ファイル | 既定 |
|---|---|
| `.spec/core-rules.md` | R-D01〜D06（silent-wrong 禁止、未検証 negative の禁止、比較の公平性 等） |
| `.spec/invariants.md` | INV-D01〜D05（worktree 必須、相対パス、data/shared、3点セット、negative の格付け） |
| `.spec/known-issues.md` | KI-D01〜D13（silent-wrong 4類型、再現性、品質ゲート崩壊、研究の進め方） |

**このスキルの仕事は、既定を埋めることではなく「プロジェクト固有」節を埋めることです。**
既定だけでも `/task-run` は動きますが、プロジェクト固有の失敗パターンは既定では捕捉できません。

## 設計方針: 白紙の質問をしない

インタビュー形式は記入負担が高く、結局埋められません。
**既存資産から候補を機械的に拾い、ユーザーは確認・修正するだけ**にします。

## Workflow

### Step 1: 現状の把握と証拠収集

```bash
bash .claude/skills/spec-init/gather-evidence.sh
```

以下を出力します。

1. 3ファイルの記入状況（未作成 / 既定のみ / 固有あり）
2. `known-issues` 候補: closed した `bug` ラベル Issue、`wontfix` Issue、revert コミット
3. `core-rules` 候補: CLAUDE.md 中の禁止・必須表現
4. `invariants` 候補: `docs/` の設計文書、closed の `feature` / `refactor` Issue

**ファイルが存在しない場合**は、テンプレートから復元するようユーザーに伝えて中断すること
（既定を失った状態で埋めさせない）。

### Step 2: known-issues の候補提示 ── ここを最優先

**過去の bug がプロジェクト固有の失敗パターンの最良の情報源**です。ここから始めます。

Step 1 で得た closed bug Issue を、**既定 KI-D01〜D13 に該当しないもの**に絞って提示します。
既定で捕捉済みのものを重複登録しないこと。

各候補について Issue 本文を読み、以下の形に整形して提示します。

```markdown
### KI-001: <失敗の名前>

**症状**: <どう見えたか>
**真因**: <実際の原因>
**誤った対処**: <最初に試して間違っていた対処>
**正しい対処**: <最終的に効いた対処>
**発生日**: YYYY-MM-DD
**関連Issue**: #N
```

**「誤った対処」が Issue から読み取れない場合は、ユーザーに質問すること。**
ここが最も価値のある情報であり、埋まっていない登録は意味が薄い。

各候補に対し **採用 / 修正して採用 / 却下** を選んでもらいます。
一度に大量に出さず、**5件ずつ**提示して進めること。

### Step 3: core-rules の確認

既定 R-D01〜D06 でカバーされない、プロジェクト固有の絶対ルールを尋ねます。

質問例:
- このプロジェクトで「どんな理由があっても壊してはいけない」ものは何ですか
- 過去に「これをやって大事故になった」ことはありますか
- 外部に公開・提出する成果物に関する制約はありますか（機密、ライセンス、再現性要件）

**理由が書けないものは絶対ルールではない**ため、`invariants.md` か CLAUDE.md に回すこと。

### Step 4: invariants の確認

既定 INV-D01〜D05 でカバーされない設計判断を尋ねます。

質問例:
- 既に決めていて、覆すなら合意が必要な設計判断は何ですか
- データ形式・ディレクトリ構成・命名で固定しているものはありますか
- 使わないと決めた技術・手法はありますか（理由つきで）

Step 1 で拾った closed の `feature` / `refactor` Issue から候補を提示します。

### Step 5: 書き込み

**各ファイルの「プロジェクト固有」節にのみ追記します。**

- **既定の節は絶対に書き換えない**
- 既存のプロジェクト固有項目も消さない（**追記のみ**）
- `（未記入）` のプレースホルダは、最初の項目を追加する時に削除する
- 採番はファイル内で連番（`KI-001`, `KI-002`, ...）。既定の `KI-D0x` とは別系列

### Step 6: 確認

```bash
bash .claude/skills/spec-init/gather-evidence.sh
```

を再実行し、記入状況が更新されたことを示します。

あわせて、`auto-reviewer` の停止条件が解除されている（＝ファイルが存在し既定が保たれている）ことを伝えます。

## 再実行について

このスキルは**何度でも実行できます**。失敗を経験するたびに `/spec-init` で
`known-issues.md` に追記していくのが本来の使い方です。

再実行時は、既に登録済みの項目を候補から除外してください。

## 注意

- **既定を削除しないこと。** 削除すると `auto-reviewer` が停止条件と判定する
- サーベイ結果や調査記録そのものを書かないこと。それらは `docs/surveys/` に置く。
  ここに書くのは**次に同じ失敗をしないための行動指針**だけ
- 抽象的すぎる項目（「バグを作らない」等）は登録しない。**再発を検知できる具体性**が必要
