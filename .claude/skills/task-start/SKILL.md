# Task Start

**task 層の入口。** 現在の状態と目標の状態を対話で引き出し、task と既定構成の子 issue を作成する。
最後に「そのまま実行するか」を確認し、yes なら `/task-run` を呼ぶ。

```
/task-start 提案手法Xが既存手法を上回るか検証したい
/task-start データローダの高速化 --epic 100
```

---

## ★ 最重要: 現状と目標を必ず対話で確認する

**なぜ両側を聞き出す必要があるのか**は
`.claude/rules/template/issue-hierarchy.md`「★ 現在の状態と目標の状態を必ず対話で確認する」に
定義されている（セッション開始時に自動読込されるルール）。本スキルはその実施手順である。

本スキル固有の補足:

- **「何ができたら goal か」を具体化する。** 達成を判定できる状態まで降ろす
- 即答できない場合は `/qa-ask` で非同期に投げて作業を続行する

質問の型は Step 2（現在の状態）と Step 3（目標の状態）に列挙してある。

---

## Workflow

### Step 1: epic の確認

`--epic` が指定されていればその goal を読む。無ければ既存 epic を提示して選ばせるか、
新規 epic を作るかを確認する。

```bash
gh issue list --label epic --state open --json number,title -q '.[]|"#\(.number)\t\(.title)"'
```

**epic の goal を読み上げ、この task がそこに貢献することを確認する。**

### Step 2: 現在の状態を聞く

```
- 今、どこまでできていますか（動くもの / 部分的に動くもの / まだ無いもの）
- 今の実装で「ここは信用してよい」と言える部分はどこですか
  逆に「怪しい」と思っている部分はありますか
- 使えるデータ・環境・計算資源は何がありますか
- すでに試して駄目だったことはありますか
```

**2つ目の質問が特に重要。** 「信用してよい部分」と「怪しい部分」の区別は、
後で negative が出たときに実装バグを疑う起点になる。
ここが曖昧なまま進むと silent-wrong の切り分けができない
（`.spec/known-issues.md` KI-D01〜D04 参照）。

**現状は毎回確認し直すこと。** 前の task の記述を引き継がない。
前 task で「動くようになった」はずのものが実は silent-wrong だった場合、
誤った現状認識がそのまま次の前提になり負債が累積する。

### Step 3: 目標の状態を聞く

```
- これができたら成功、と言えるものを一つ挙げるとしたら何ですか
- うまくいったとき、その結果を誰に見せますか（論文 / 社内 / 自分の判断材料）
- いま何に困っていて、それが解消されるとどう変わりますか
- 似たことを既にやっている人はいますか。あるなら何が足りないと思いますか
- 逆に、どうなったら「これはダメだった」と判断しますか
- いつまでに、どのくらいの手間をかけられますか
```

**最後から2番目が negative の意味の事前登録にあたる。**
結果を見る前に宣言しておけば、後から baseline を強化して意味を書き換える余地が減る。

### Step 4: task 本文の作成

```markdown
## 現在の状態（この task 作成時点）

- **動いているもの**: <検証済みで信用してよい部分>
- **怪しいもの**: <動いているように見えるが未検証の部分>
- **無いもの**: <これから作る必要があるもの>
- **利用可能な資源**: <データ / 環境 / 計算資源>
- **既に試して駄目だったこと**: <再実行を避けるため>

## 目標の状態

- **貢献先**: epic #N の「<goal を引用>」
- **成功条件**: <測定可能な形で>
- **negative の意味**: <期待した結果が出なかったとき何が言えるか>
- **既存手法**: <既に解けている可能性。survey issue で本格確認>
- **想定コスト**: <概算の issue 数 / 期間>

## 未確定

- <聞いたが答えが得られなかった項目> → <解消担当>
```

**「現在の状態」と「目標の状態」の差分が、この task で埋めるもの**である。
差分が明確でない場合、task はまだ切れる状態にない。ユーザーにそう伝えて中断すること。

### ★ 「未確定」の記述形式（定義。他スキルはここを参照する）

**未確定項目には必ず解消担当を併記する。** 担当のない未確定は
「誰も確定させないまま実装に入る」ことを意味し、エージェントが空白を埋めて goal を発明する。

```markdown
## 未確定

- データ入手可否・ライセンス → survey
- 再現判定の許容差 → spec
- ハイパーパラメータの既定値 → #123
```

| 記法 | 意味 |
|---|---|
| `→ <種類ラベル>` | そのラベルを持つ子 issue が担当。**task 作成時点では子が未採番**なので通常はこちら |
| `→ #<番号>` | その issue が担当 |

**読み取りは正規化して行う。** 太字などの装飾（`→ **survey**`）と末尾の補足
（`→ spec（事前登録）`、`→ survey で先に洗い出す`）は無視し、
**先頭の種類ラベル名または `#番号` のみ**を担当として解決する。

**構造化メタデータ（YAML 等）は使わない。** 1行注記で足りる（KISS）。

`/task-run` はこの形式を読んで停止/続行を判定し、担当 issue が閉じた時点で再照合する。
**判定表は `/task-run` Step 0-2 にあり、ここには再掲しない**（2箇所に書くと必ず食い違う）。

### ★ 「目標の状態」を未確定に逃がさない

**成功条件と negative の意味は、この task 単位で確定していなければならない。**
下位パラメータ（許容差の数値・データの入手先）が未確定でも、
**「何ができたら成功か」は言えるはず**である。

```markdown
❌ - **成功条件**: spec issue で決める
❌ - **成功条件**: survey の結果次第
✅ - **成功条件**: 比較表の全セルが埋まり、事前登録した許容差で判定されている
                （許容差の数値は spec で事前登録 → 未確定節に記載）
```

**委譲先を書いただけの成功条件は「空欄」と同じ**である。goal の実質を下位パラメータに
偽装して自動処理を通す抜け道になるため、`/task-run` はこれを空欄として停止する。

### Step 5: task の作成

```
Skill(skill="issue-create", args="--type task --title <題> --parent <epic番号>")
```

### Step 6: 既定構成の子 issue を生成

**既定構成は必須。** 省略する場合は task 本文に理由を記載すること。

**構成表は `.claude/rules/template/issue-hierarchy.md`「既定の task 構成（必須）」が単一情報源。**
task の種類（新手法の検証 / 既存実装の改善 / バグ修正 / 調査のみ / 基盤整備）に対応する
issue 列をそこから読み、その順に作成する。ここには表を再掲しない（二重管理で内容がずれるため）。

各 issue を `/issue-create` で作成し、task の子としてリンクする。

```
Skill(skill="issue-create", args="--type survey --title ... --parent <task番号>")
Skill(skill="issue-create", args="--type spec --title ... --parent <task番号>")
...
```

#### survey の扱い

理由と「2周目以降も skip しない」規定は
`.claude/rules/template/issue-hierarchy.md`「survey を先頭に置く理由」を参照。

**運用上の帰結**: 2周目以降の task でも survey issue を必ず作る。
不要と判断した場合も skip せず、判断の記録を残して閉じる。

### Step 7: 実行確認

作成した task と子 issue の一覧を示し、**そのまま実行するかを確認する。**

```
┌─────────────────────────────────────────────────────────────┐
│ task #101「基礎検証」を作成しました                          │
├─────────────────────────────────────────────────────────────┤
│ 子 issue:                                                    │
│   #102 survey     先行研究の調査                             │
│   #103 spec       仕様の作成                                 │
│   #104 feature    実装                                       │
│   #105 validation 実装の動作確認                             │
│   #106 experiment 仮説検証                                   │
│                                                              │
│ 未確定の項目: <あれば列挙>                                   │
│                                                              │
│ このまま実行しますか？                                       │
│ [はい、/task-run で実行する]                                 │
│ [いいえ、あとで実行する]                                     │
└─────────────────────────────────────────────────────────────┘
```

**「はい」なら続けて `/task-run` を呼ぶ。**

```
Skill(skill="task-run", args="#<task番号>")
```

**未確定の項目が残っている場合は、その旨を明示してから確認すること。**

**未確定項目が残ること自体は問題ない。** データ入手可否・許容差のように
survey / spec を実施して初めて確定する項目は、事前に埋めれば「調べる前に答えを書く」ことになる。

**問題なのは担当が書かれていないこと**である。担当のない未確定を残したまま実行すると、
エージェントが空白を埋めて goal を発明する。Step 4 の記述形式に従い、
**全ての未確定項目に解消担当を併記してから**確認に進むこと。

## ゴールの不変性

`.claude/rules/template/issue-hierarchy.md`「★ ゴールの不変性」に従う。

**本スキルでの適用**: Step 1 で epic の goal を**読み上げるだけ**にとどめ、
この task に合わせて書き換えない。goal 自体を変える必要が生じた場合は
task を作らず、新しい epic を立てる判断をユーザーに求める。
