# Task Start

**task 層の入口。** 現在の状態と目標の状態を対話で引き出し、task と既定構成の子 issue を作成する。
最後に「そのまま実行するか」を確認し、yes なら `/task-run` を呼ぶ。

```
/task-start 提案手法Xが既存手法を上回るか検証したい
/task-start データローダの高速化 --epic 100
```

---

## ★ 最重要: ユーザーは十分な説明をしない

**ユーザーはほとんどの場合、エージェントにとって十分な量の説明をしない。**
これは怠慢ではなく、本人にとって自明な前提が言語化されないという普遍的な現象である。

しかも欠けるのは goal（目標の状態）だけではない。**現状の認識も共有が崩れている。**

task とは「**現在地から目的地までの距離**」である。どちらか一方だけ合意しても距離を測り違える。

| 崩れるもの | 起きること |
|---|---|
| 目標の状態が曖昧 | エージェントが goal を発明し、以降それがぶれ続ける |
| 現在の状態が曖昧 | 動くはずの部分が動いていない / 既に試して駄目だったことを再度やる / 存在しないデータを前提にする |

**受け取った説明をそのまま記録してはならない。** 両側を能動的に聞き出すこと。

### 対話の原則

1. **平易な言葉で聞く。** 「成功条件を定義してください」ではなく、本人の言葉で答えられる質問にする
2. **「何ができたら goal か」を具体化する。** 達成を判定できる状態まで降ろす
3. **答えられない項目は推測で埋めない。** 「未確定」として残し、後で確定させる
4. 即答できない場合は `/qa-ask` で非同期に投げて作業を続行する

## Workflow

### Step 1: epic の確認

`--epic` が指定されていればその goal を読む。無ければ既存 epic を提示して選ばせるか、
新規 epic を作るかを確認する。

```bash
gh issue list --label epic --state open --json number,title -q '.[]|"#\(.number)\t\(.title)"'
```

**epic の goal を読み上げ、この task がそこに貢献することを確認する。**

### Step 2: 現在の状態を聞く

```
- 今、どこまでできていますか（動くもの / 部分的に動くもの / まだ無いもの）
- 今の実装で「ここは信用してよい」と言える部分はどこですか
  逆に「怪しい」と思っている部分はありますか
- 使えるデータ・環境・計算資源は何がありますか
- すでに試して駄目だったことはありますか
```

**2つ目の質問が特に重要。** 「信用してよい部分」と「怪しい部分」の区別は、
後で negative が出たときに実装バグを疑う起点になる。
ここが曖昧なまま進むと silent-wrong の切り分けができない
（`.spec/known-issues.md` KI-D01〜D04 参照）。

**現状は毎回確認し直すこと。** 前の task の記述を引き継がない。
前 task で「動くようになった」はずのものが実は silent-wrong だった場合、
誤った現状認識がそのまま次の前提になり負債が累積する。

### Step 3: 目標の状態を聞く

```
- これができたら成功、と言えるものを一つ挙げるとしたら何ですか
- うまくいったとき、その結果を誰に見せますか（論文 / 社内 / 自分の判断材料）
- いま何に困っていて、それが解消されるとどう変わりますか
- 似たことを既にやっている人はいますか。あるなら何が足りないと思いますか
- 逆に、どうなったら「これはダメだった」と判断しますか
- いつまでに、どのくらいの手間をかけられますか
```

**最後から2番目が negative の意味の事前登録にあたる。**
結果を見る前に宣言しておけば、後から baseline を強化して意味を書き換える余地が減る。

### Step 4: task 本文の作成

```markdown
## 現在の状態（この task 作成時点）

- **動いているもの**: <検証済みで信用してよい部分>
- **怪しいもの**: <動いているように見えるが未検証の部分>
- **無いもの**: <これから作る必要があるもの>
- **利用可能な資源**: <データ / 環境 / 計算資源>
- **既に試して駄目だったこと**: <再実行を避けるため>

## 目標の状態

- **貢献先**: epic #N の「<goal を引用>」
- **成功条件**: <測定可能な形で>
- **negative の意味**: <期待した結果が出なかったとき何が言えるか>
- **既存手法**: <既に解けている可能性。survey issue で本格確認>
- **想定コスト**: <概算の issue 数 / 期間>

## 未確定

- <聞いたが答えが得られなかった項目。推測で埋めない>
```

**「現在の状態」と「目標の状態」の差分が、この task で埋めるもの**である。
差分が明確でない場合、task はまだ切れる状態にない。ユーザーにそう伝えて中断すること。

### Step 5: task の作成

```
Skill(skill="issue-create", args="--type task --title <題> --parent <epic番号>")
```

### Step 6: 既定構成の子 issue を生成

**既定構成は必須。** 省略する場合は task 本文に理由を記載すること。

| task の種類 | 既定の issue 構成 |
|---|---|
| 新手法の検証 | survey → spec → feature → validation → experiment |
| 既存実装の改善 | spec → feature → validation |
| バグ修正 | bug（単独。validation を伴う場合あり） |
| 調査のみ | survey（単独） |
| 基盤整備 | spec → feature → validation |

各 issue を `/issue-create` で作成し、task の子としてリンクする。

```
Skill(skill="issue-create", args="--type survey --title ... --parent <task番号>")
Skill(skill="issue-create", args="--type spec --title ... --parent <task番号>")
...
```

#### survey を先頭に置く理由

**novelty / baseline 監査を手順そのものにするため。**

「既存手法で既に解けるか」の確認が後回しになると、複数段を消化した後に
「古典手法で厳密に解ける」と判明して全結果が無価値になる事故が起きる（実際に観測されている）。
サイクルの1番目に固定すれば忘れようがない。

#### 2周目以降も survey を skip しない

同じ epic で2周目以降の task を作る場合も、**survey issue を省略してはならない。**

内容は「ゼロからの文献調査」ではなく、
**「ここまでの実験結果を踏まえて、追加のサーベイが必要か」の検討**である。

**「不要」と判断した場合も、skip ではなく判断の記録を残して閉じる。**
省略を許すと実質的に毎回省略されるようになる。

**結果が出るたびに探すべき場所が変わる。** だから survey は1回きりではなくサイクルの一部である。

### Step 7: 実行確認

作成した task と子 issue の一覧を示し、**そのまま実行するかを確認する。**

```
┌─────────────────────────────────────────────────────────────┐
│ task #101「基礎検証」を作成しました                          │
├─────────────────────────────────────────────────────────────┤
│ 子 issue:                                                    │
│   #102 survey     先行研究の調査                             │
│   #103 spec       仕様の作成                                 │
│   #104 feature    実装                                       │
│   #105 validation 実装の動作確認                             │
│   #106 experiment 仮説検証                                   │
│                                                              │
│ 未確定の項目: <あれば列挙>                                   │
│                                                              │
│ このまま実行しますか？                                       │
│ [はい、/task-run で実行する]                                 │
│ [いいえ、あとで実行する]                                     │
└─────────────────────────────────────────────────────────────┘
```

**「はい」なら続けて `/task-run` を呼ぶ。**

```
Skill(skill="task-run", args="#<task番号>")
```

**未確定の項目が残っている場合は、その旨を明示してから確認すること。**
未確定のまま実行すると、エージェントが空白を埋めて goal を発明する。

## ゴールの不変性

**epic の goal は変更しない。** 追加 task を作る際は既存の goal を読み直し、
「この goal に照らして必要か」を判断する。

**結果に合わせて goal を書き換えることは禁止。**
これは実際に観測された失敗であり、書き換えると以降の判断すべてが新しい goal を基準に行われ、
ずれが自己強化する。

goal 自体を本当に変える必要がある場合は、**新しい epic を立てる。**
旧 epic は「この goal は達成されなかった」という記録として閉じる。
