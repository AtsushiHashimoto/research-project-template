# task 本文の雛形と「未確定」の書式（/task-start が本文を書くときだけ読む）

```markdown
## 現在の状態（この task 作成時点）

- **動いているもの**: <検証済みで信用してよい部分>
- **怪しいもの**: <動いているように見えるが未検証の部分>
- **無いもの**: <これから作る必要があるもの>
- **利用可能な資源**: <データ / 環境 / 計算資源>
- **既に試して駄目だったこと**: <再実行を避けるため>

## 目標の状態

- **貢献先**: epic #N の「<goal を引用>」
- **成功条件**: <測定可能な形で。1 文の合否の述語>
- **negative の意味**: <期待した結果が出なかったとき何が言えるか>
- **既存手法**: <既に解けている可能性。survey issue で本格確認>
- **想定コスト**: <概算の issue 数 / 期間>

## 未確定

- <聞いたが答えが得られなかった項目> → <解消担当>
```

## 「未確定」の書式（定義）

| 記法 | 意味 |
|---|---|
| `→ <種類ラベル>` | そのラベルを持つ子 issue が担当（task 作成時点では子が未採番なので通常はこちら） |
| `→ #<番号>` | その issue が担当 |

- 装飾（`→ **survey**`）と後ろの補足（`→ spec（事前登録）`）は無視し、先頭の種類ラベル名か `#番号` を担当とする
- 構造化メタデータ（YAML 等）は使わない

## 「目標の状態」を未確定に逃がさない

成功条件と negative の意味はこの task 単位で確定させる。下位パラメータ（許容差の数値・データの入手先）だけを未確定にする。

```markdown
❌ - **成功条件**: spec issue で決める
✅ - **成功条件**: 比較表の全セルが埋まり、事前登録した許容差で判定されている
                （許容差の数値は spec で事前登録 → 未確定節に記載）
```

委譲先を書いただけの成功条件は空欄と同じである。
