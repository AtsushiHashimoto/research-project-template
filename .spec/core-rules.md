# Core Rules（絶対ルール）

> このファイルは `auto-reviewer` エージェントが**判断前に必ず読む**必須コンテキストです。
> 空のまま運用すると `/issue-auto` の自信度ゲートが根拠を失います。プロジェクト開始時に埋めてください。

ここには「**どんな理由があっても破ってはならないルール**」だけを書きます。
判断に迷う余地のあるものは `invariants.md`（設計判断）または CLAUDE.md（作業手順）に書いてください。

## 書き方

各ルールは「禁止事項」と「理由」をセットで書きます。理由が書けないルールは絶対ルールではありません。

```markdown
### R-001: <ルール名>

**禁止**: <何をしてはいけないか>
**理由**: <なぜ破ってはいけないか>
**例外**: <あれば。無ければ「なし」>
```

# 既定のルール（テンプレート同梱）

実プロジェクトの失敗実績から導いた、**分野を問わず適用される**絶対ルールです。
**削除しないでください。** プロジェクト固有のものは下の節に追記してください。

### R-D01: 前提が崩れた入力を黙って受理しない

**禁止**: 想定外の入力形式・状態に対して、例外を出さずに既定値やそれらしい値を返すこと
**理由**: silent-wrong は false negative の最大の原因。クラッシュしないため気づかれず、
「手法が効かない」という誤った結論として確定してしまう
**例外**: 承認済み Fallback ホワイトリスト（設定の既定値、キャッシュミス、UI プレースホルダ）のみ
**関連**: [[known-issues.md]] KI-D03

### R-D02: 検証していない negative を結論として扱わない

**禁止**: positive/sanity control を通していない negative result を「効かない」という結論として記録・伝播させること
**理由**: 検出力が担保されていない null は科学的 null ではなく、実装バグのアーティファクトでありうる
**例外**: なし。手続き未了なら `unverified-negative` と明記して保留する
**関連**: CLAUDE.md「実験の規律」、KI-D11

### R-D03: 比較の公平性を崩さない

**禁止**: baseline にのみ、提案手法が持たない工夫を投入して比較すること
**理由**: 不公平な比較で得た「提案手法が負けた」は、手法の評価ではなく比較設計の失敗である
**例外**: 「baseline の上限測定」として目的を明示し、優位性の検証としては扱わない場合
**関連**: CLAUDE.md「実験の規律」§2

### R-D04: 実験結果の数値を再実行せずに書き換えない

**禁止**: 記録済みの実験結果を、再実行を伴わずに手で修正すること
**理由**: 再現性が失われ、以降の全ての判断の根拠が崩れる
**例外**: なし。誤記の訂正であっても、訂正した旨と根拠を併記する

### R-D05: テストが動いていない状態を「通っている」と扱わない

**禁止**: collection error や実行スキップが起きている状態で、テストが通ったと判定すること
**理由**: 「失敗0件」と「実行0件」は全く違う。後者を前者と誤認すると全判断の根拠が失われる
**例外**: なし
**関連**: KI-D07

### R-D06: 対症療法で挙動を上書きしない

**禁止**: 想定と異なる挙動に対し、根本原因を特定せずに出力側で辻褄を合わせること
**理由**: 原因が残ったまま観測できなくなり、後段でより大きな誤りとして顕在化する
**例外**: なし。暫定回避が必要な場合も、根本原因の Issue を必ず立てる
