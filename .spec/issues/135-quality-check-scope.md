# Issue #135 仕様: quality-check を変更ファイル限定にする

- 状態: approved（auto-reviewer 判断済み。警告と追加 V を反映。ログ: 135-auto-decisions.md）
- 出自: PR #129 / `omron-sinicx/delta-clip-dev#153`

## 背景（下流の実測）

`quality-check.sh` の shellcheck が `git ls-files '*.sh'` で**ツリー全件を走査する**ため、
**シェルを1行も触っていない PR が既存の指摘で FAIL** する。

下流プロジェクトの実測: 31ファイルに 32件の指摘（うちテンプレート同梱の
`resolve-model.sh` に2件）。Python だけを変更した PR も通らない。

同一スクリプト内の**非対称**でもある — Python の format 検査は変更ファイル限定なのに
shellcheck だけが全件。

## なぜ #121 で解決していないのか

#121 は「**テンプレート自身の** 23件を潰す」ことで全件走査を成立させた。
しかし**派生プロジェクトは自前のスクリプトを持つ**ので、同じ問題がそのまま再発する。
**テンプレートが緑でも下流は赤**という、テンプレート開発では見えない失敗モード。

## なぜ PR #129 をそのままマージしないのか

分岐元が #121 より前。マージすると **#121 を丸ごと巻き戻す**
（実行/未実行サマリ、bash 3.2 互換化、shebang 判定による対象拡張、
既存23件の解消、`warn_missing` の分離がすべて消える）。

**指摘を #121 の成果の上に再実装する。**

## 設計

### D1: base ref の解決（PR #129 の実装を踏襲）

```
QUALITY_BASE_BRANCH が設定されていればそれを使う（無効なら失敗）
→ origin/HEAD から既定ブランチを取得（取れなければ main）
→ origin/<default> → <default> の順に存在するものを使う
```

**★ #122 D4 との整合**: テンプレートは「既定ブランチは `main` 固定」を規約化している
（`git-workflow.md`）。`origin/HEAD` からの検出は #122 で**採らなかった**方針だが、
ここでは**検出できなければ `main` にフォールバックする**形なので規約と矛盾しない。
検出は「派生プロジェクトが別名を使っていても動く」ための保険であり、
規約そのものを緩めるものではない。この位置づけをコメントに書く。

### D2: 変更ファイルの算出

`merge-base HEAD <base>` からの差分 ＋ 未コミットの変更 ＋ 未追跡ファイルの和。
**削除されたファイルは除外**（`--diff-filter=d`）。

### D3: ファイル単位の検査を変更ファイルに限定する

対象は **shellcheck** と **Python の ruff**。

**★ mypy は限定しない（auto-reviewer 警告1）**: 型エラーは**ファイル間を伝播する**。
シグネチャを変えると未変更の呼び出し側が壊れるうえ、mypy 既定の `follow-imports` は
未変更ファイルのエラーも報告する。shellcheck / ruff と同型に扱えない。

**★ 限定の取り方（警告2）**: 「**#121 の収集ロジック（`*.sh` ＋ shebang 判定）∩ 変更ファイル**」
とする。PR #129 の `changed_of sh` は**拡張子マッチのみ**で、
`claude-san` のような拡張子なしスクリプトが素通りする。

**限定しないもの**:

- `rules MANIFEST 整合`（ツリー全体の整合性が対象）
- `スキル参照名の実在` / `スキルのラベル定義`（#117〜#119。**横断的な整合性検査**であり、
  変更ファイルだけ見ても意味がない。例: スキルを1つ消したとき、
  それを参照する側のファイルは変更されていない）
- `pytest`（テスト全体を回すのが本来の目的）

### D4: 全件走査を明示的に選べるようにする

`QUALITY_SCOPE=all-files`（仮）または `QUALITY_FULL_SCAN=1` で全件走査に切り替えられる。

**★ 既存の `QUALITY_SCOPE` との衝突に注意**: `QUALITY_SCOPE` は既に
`docs` / `all` の2値で「**どの種類の検査を回すか**」を表しており、
「**どの範囲のファイルを見るか**」とは別の軸である。
**別の環境変数にする**（`QUALITY_FULL_SCAN=1`）。同じ変数に2つの意味を持たせない。

`QUALITY_SCOPE=docs` のときは **scope 計算自体を行わない**（該当検査が走らないため）。

### D5: 限定したことを必ず表示する（無言の切り捨て禁止）

`shellcheck (3 files, 変更ファイルのみ)` のように**範囲と件数を出す**。
base ref が解決できず全件にフォールバックした場合も、その旨と理由を表示する。
**解決した base ref 自体も表示する。** 限定時の表示には
「全件は `QUALITY_FULL_SCAN=1`」の導線を1行入れる。

### D6: 回帰テストを取り込む

PR #129 の `tests/test_quality_check_scope.sh` を取り込む。
**ただし #121 の成果を守る観点を追加する**（サマリ機能・`warn_missing`・
bash 3.2 互換が残っていることを pin する）。

**★ そのまま取り込まない（auto-reviewer 警告）。** 原案は本仕様と3箇所で矛盾する:

| 原案の項目 | 矛盾 | 対応 |
|---|---|---|
| 4「base 解決不能なら FAILED=1」 | 本仕様の Fallback（全件走査）と衝突。**V6 と V11 が同時に満たせない** | 書き換える（フォールバックすることを pin する） |
| 1「`git ls-files '*.sh'` が無いこと」 | `QUALITY_FULL_SCAN` の全件経路で誤 FAIL しうる | 全件経路を除外して判定 |
| 5「`--source-path=SCRIPTDIR`」 | 現行 #121 実装に無い（`-x` なしで 0 件達成済み） | **採らない**（理由を記載） |

## Fallback ホワイトリスト

1. **base ref が解決できない場合は全件走査にフォールバックする**
   （新規リポジトリで `main` すら無い、shallow clone 等）。
   検査を飛ばすより全件走査するほうが安全側。**ただし理由を必ず表示する**。

   全件走査は限定走査の**厳密な上位集合**なので、検出漏れ方向の silent-wrong を生まない。
   PR #129 は即 FAIL としているが、`main` が本当に無い新規リポジトリで
   完了ゲートが恒久的に赤くなり KI-D08（RED 常態化）を招くため**意図的に逸脱する**。

## 許容するトレードオフ（記録）

**「PR で触っていない既存の指摘」は検出されなくなる。** これは #129 の指摘に内在し、
拒否すると親 task の goal に反する。許容の条件として D5 の導線（`QUALITY_FULL_SCAN=1`）を
出力とヘッダコメントに明記する。**定期的な全件走査の組み込みは本 issue のスコープ外**
（goal を広げないため。必要なら別 issue）。
