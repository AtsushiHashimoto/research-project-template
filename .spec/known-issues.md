# Known Issues（過去の失敗パターン）

> このファイルは `auto-reviewer` エージェントが**判断前に必ず読む**必須コンテキストです。
> 同じ失敗を繰り返さないための記録です。失敗するたびに追記してください。

ここには「**一度やって失敗したこと**」を書きます。
成功パターンではなく**失敗パターン**を書くことが重要です。エージェントは同じ罠を繰り返し踏みます。

## 書き方

```markdown
### KI-001: <失敗の名前>

**症状**: <どう見えたか>
**真因**: <実際の原因>
**誤った対処**: <最初に試して間違っていた対処>
**正しい対処**: <最終的に効いた対処>
**発生日**: YYYY-MM-DD
**関連Issue**: #N
```

**「誤った対処」を必ず書いてください。** エージェントが最初に飛びつく仮説こそが再発します。

# 既定の失敗パターン（テンプレート同梱）

実プロジェクト（Issue 579件規模の機械学習研究プロジェクト）の bug / wontfix 実績から抽出した、
**分野を問わず再発する**失敗パターンです。

**この既定は削除しないでください。** 抽象度が高く、ほぼ全ての研究プロジェクトで再発します。
プロジェクト固有のものは下の「プロジェクト固有」節に追記してください。

## ★ 最重要: silent-wrong 系（例外を出さずに間違った結果を返す）

**false negative を量産する最大の原因。** クラッシュしないため気づかれず、
「手法が効かない」という誤った結論として確定してしまう。
抽出元プロジェクトの Critical / High バグの過半がこの類型だった。

### KI-D01: 符号・方向・真偽が反転している

**症状**: 学習が進まない / 性能が baseline を下回る / 最適化が逆方向に動く
**真因**: 勾配の符号、大小関係、真偽値の対応が反転している
**誤った対処**: 「この手法は効かない」と結論する / ハイパーパラメータ探索を広げる
**正しい対処**: 既知の正解を持つ最小ケースで**出力の向き**を直接検証する。
最適化なら「1ステップで損失が下がるか」を assert する

### KI-D02: 変換・前処理が入力の一部を無視している

**症状**: 手法の理論的保証が成り立たない / 特定条件でのみ性能が出ない
**真因**: 二値化・正規化・射影などの変換が、必要な入力を使っていない
**誤った対処**: 理論の前提が実データで成り立たないと解釈する
**正しい対処**: 変換関数が**満たすべき性質**を test で pin する（入出力の対応を直接検証する）

### KI-D03: 前提が崩れた入力を黙って受理する

**症状**: 一部の設定でのみ結果がおかしい。エラーは出ない
**真因**: 想定外の入力形式に対して関数が raise せず、意味の無い値を返している
**誤った対処**: 「その設定は相性が悪い」と結論する
**正しい対処**: **前提が崩れたら必ず raise する。** 黙ってフォールバックしない

### KI-D04: 評価データに答えが混入 / 評価条件が揃っていない

**症状**: 性能が異常に高い、または比較条件によって結論が反転する
**真因**: 正解構造が訓練データにも入っている / 評価時のノイズ・前処理条件が実験間で不一致
**誤った対処**: 数値をそのまま採用して結論を出す
**正しい対処**: 正解構造は評価側にのみ配置する。評価条件を固定し、変更時は既存結果を**再評価**する

## 再現性

### KI-D05: 乱数状態が checkpoint されず resume で再現できない

**症状**: 中断・再開した実験が、通しで実行した場合と一致しない
**真因**: モデル重みは保存されるが、サンプラーや生成器の乱数状態が保存されていない
**誤った対処**: 「実行ごとのばらつき」として片付ける
**正しい対処**: 乱数状態を checkpoint に含め、resume の一致を test で確認する

### KI-D06: 依存が未宣言で fresh 環境では動かない

**症状**: 手元では動くが、新しい環境や CI で import に失敗する
**真因**: 手動インストールした依存が宣言ファイルに入っていない
**誤った対処**: 環境固有の問題として個別に手当てする
**正しい対処**: fresh 環境での再現を定期的に確認する

## 品質ゲートの崩壊

### KI-D07: 収集エラーで全テストが「実行されていない」状態になる

**症状**: テストが「失敗」ではなく「実行されていない」
**真因**: import エラーやシグネチャ不一致で collection error が起き、全体が RED
**誤った対処**: RED を既知として放置し実装を進める
**正しい対処**: **collection error は最優先で直す。** テストが動いていない状態で
「テストが通っている」と誤認すると、以降の全判断の根拠が失われる

### KI-D08: 品質ゲートの RED を常態化させる

**症状**: lint / 型チェックのエラーが数十件たまり、誰も見なくなる
**真因**: RED を放置したまま新規作業を重ねた
**誤った対処**: 「後でまとめて直す」— 実際には返済されない
**正しい対処**: RED は発生時に直す。まとめて直す Issue は**着手されないまま wontfix になりやすい**
（抽出元プロジェクトでも、lint 負債の一括解消 Issue が実際に wontfix で終わっている）

## 資源・数値の安定性

### KI-D09: 数値が発散する / 境界値でクラッシュする

**症状**: NaN・Inf が出る、特定パラメータ（0 など）でクラッシュする
**真因**: 境界値の扱いが未定義、正規化の欠落
**誤った対処**: 学習率を下げる等の対症療法で回避する
**正しい対処**: **発生箇所を特定してから**最小修正する。境界値をテストに含める

### KI-D10: 終了条件のないループ / 想定外のメモリ増

**症状**: 特定条件でハングする、OOM する
**真因**: rejection サンプリング等に上限が無い / 事前計算の範囲を広げすぎた
**誤った対処**: 実行環境のスペックを上げる
**正しい対処**: 上限を設ける。メモリ増を伴う変更は前後で実測して記録する

## ★ 研究の進め方（メタ）

### KI-D11: 全方向が negative で終わったとき、個別の negative として扱う

**症状**: 探索した方向がすべて「効かない」で閉じ、成功事例が1つも残らない
**真因**: 個々の negative が独立に正しいとは限らない。**共通のワークフロー上の欠陥**
（実装バグの見逃し、不公平な baseline、検出力不足、ゲート順序の誤り）が全体に効いている可能性がある
**誤った対処**: 「この研究方向には見込みが無い」と総括して終える
**正しい対処**: 全方向 negative は**それ自体が異常信号**として扱う。
少なくとも1方向について positive control と実装検証をやり直してから総括する。
CLAUDE.md「実験の規律」を全 negative 結論に**遡って**適用する

> この項目は、抽出元プロジェクトが最終的に全方向 negative で閉じたという事実そのものから導かれている。

### KI-D12: novelty / baseline 監査を後段に置く

**症状**: 複数段を消化した後で「既存手法が既に厳密に解ける」と判明し、全結果が無価値になる
**真因**: 「既存手法で解けるか」の確認が探索の最初のゲートになっていなかった
**誤った対処**: 段階分解のプロセス自体を疑う
**正しい対処**: **段0 として novelty / baseline 監査を置く。** 既存手法で解けるなら以降の段は実行しない

### KI-D13: 引用・出典を照合せずに設計判断の根拠にする

**症状**: もっともらしい主張が特定の文献に帰属されているが、実際には書かれていない
**真因**: 検索結果の要約を一次資料と照合せずに採用した
**誤った対処**: 引用が正しい前提で設計を進める
**正しい対処**: **鍵括弧引用は全文検索で照合してから使う。** 出典と証拠の強さ
（サンプル数・著者自身の留保）を併記する

### KI-D14: エージェントがゴールを勝手に変更する

**症状**: 当初の目的とずれた成果が積み上がる。振り返ると「何を達成しようとしていたか」が曖昧
**真因**: 結果に合わせて goal を書き換えた。または**そもそも goal が確定しておらず、
エージェントが空白を埋めて goal を発明した**
**誤った対処**: 新しい goal を基準に「達成した」と総括する
**正しい対処**: goal は不変とする。変更が必要なら**新しい epic を立て**、
旧 epic は「達成されなかった」記録として閉じる。
task 作成時に「現在の状態」と「目標の状態」の両方を対話で確定させ、
**答えられなかった項目は推測で埋めず「未確定」として残す**

> goal が書き換わると以降の判断すべてが新しい goal を基準に行われるため、
> **ずれが自己強化する**。書き換えた時点の記録が残らなければ後から検知もできない。
> 実プロジェクトで度々発生した。

### KI-D15: 現状認識のずれを引き継いだまま次の作業に進む

**症状**: 動くはずの部分が動いていない / 既に試して駄目だったことを再度やる /
存在しないデータを前提にする
**真因**: 前の作業で「動くようになった」はずのものが実は silent-wrong だった。
その誤った現状認識がそのまま次の前提になった
**誤った対処**: 前回の記述をそのまま引き継ぐ
**正しい対処**: **各 task の作成時に現状を毎回確認し直す。**
特に「信用してよい部分」と「怪しい部分」を区別して記録する
